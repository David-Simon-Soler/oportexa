# V0.3 DAL contract

Contrato interno, server-only, para preparar Product Discovery. El DAL consulta únicamente `core` mediante SQL parametrizado. No consulta BDNS durante requests web y nunca expone RAW, payloads, hashes internos ni detalles operacionales.

## Grant contracts

`GrantSummary` contiene el identificador BDNS, slug compatible, título nullable, tipo, presupuesto nullable, `isOpen`, fechas nullable, fecha recibida de fuente y relaciones de presentación:

- `organizations: OrganizationRef[]`;
- `regions: TaxonomyRef[]`;
- `sectors: TaxonomyRef[]`;
- `beneficiaryTypes: TaxonomyRef[]`.

Las relaciones son arrays: CORE permite N:M y el DAL no reduce permanentemente una convocatoria a una organización.

`GrantDetail` añade descripción, finalidad, bases reguladoras, URLs oficiales, fondos y provenance. Funds no son filtro ni superficie SEO en V0.3.

## Functions

- `searchGrants(filters)` devuelve resultados paginados de 20.
- `getOpenGrants(filters)` reutiliza `searchGrants` con `status=open`.
- `getGrantByCode(code)` devuelve detalle o `null`.
- `getGrantCodes()` se mantiene para sitemap existente.
- `getRegions`, `getRegionBySlug`.
- `getSectors`, `getSectorBySlug`.
- `getOrganizations`, `getOrganizationBySlug`.
- `getBeneficiaryTypes`, `getBeneficiaryTypeBySlug`.

Las funciones taxonómicas devuelven identidad estable, label, slug, total de convocatorias y abiertas.

## Filters and query parameters

Contrato V0.3:

`q`, `region`, `sector`, `beneficiary`, `status`, `minBudget`, `sort`, `page`.

Las páginas de organismo usan internamente una restricción por `source_key`; no es un parámetro de búsqueda público ni se añade a la URL de búsqueda general.

No se incluyen filtros de fecha todavía por la proporción de nulos y la semántica de `is_open` procedente de BDNS.

`minBudget` significa `total_budget >= minBudget`; los presupuestos NULL no coinciden. Valores negativos, no finitos, vacíos o excesivamente grandes se descartan durante parsing.

`page` es entero seguro desde 1; valores inválidos vuelven a 1. Los parámetros no reconocidos no entran en el contrato tipado.

## Sorting

La whitelist es:

- `recent`: `source_received_date DESC NULLS LAST`, con `last_seen_at` y BDNS como desempate;
- `budget-desc`;
- `budget-asc`.

`recent` no inventa una fecha: usa primero la fecha recibida de fuente y después el último avistamiento local. `relevance` queda PLANNED porque ILIKE no ofrece ranking real.

El SQL de ordenación sólo puede proceder de la whitelist interna.

## Slugs

Las convocatorias conservan `bdnsCode-slug-del-título` para compatibilidad. Las taxonomías usan labels normalizados; cuando hay colisión se añade `--slug-de-source-key` de forma determinista. Las regiones conservan resolución compatible por código.

No se consulta texto del usuario interpolándolo como SQL.

## Null semantics

- `null` significa dato desconocido o ausente;
- `[]` significa relación vacía;
- `false` significa estado BDNS explícitamente falso;
- `0` es un valor numérico real y no debe convertirse en ausencia.

Los fallbacks de presentación se mantienen fuera del DAL.

## Freshness and provenance

El contrato de detalle expone `source: "BDNS"`, `sourceReceivedDate`, `firstSeenAt` y `lastSeenAt`.

- `sourceReceivedDate`: fecha declarada por la fuente en CORE.
- `firstSeenAt`: primera observación local del registro.
- `lastSeenAt`: última observación local del registro.

No se expone RAW ni hashes. La UI puede comunicar fuente BDNS y observación local, pero no debe presentar timestamps locales como fecha oficial de actualización BDNS.

## SEO implications

Los contadores taxonómicos y freshness permiten decidir posteriormente si región, sector, organismo o beneficiario tienen densidad y estabilidad suficientes. No se amplía el sitemap masivamente ni se indexan búsquedas con query params.
