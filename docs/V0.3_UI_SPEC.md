# V0.3 UI Specification

Especificación funcional para iniciar Product Discovery. No define una implementación concreta ni autoriza ampliar el alcance de V0.3.

## Objetivo

Convertir Opportunity Intel en una experiencia pública útil para descubrir y entender oportunidades públicas en España.

La interfaz presentará información pública procedente de CORE, conservando la distinción entre datos oficiales y datos normalizados o derivados.

## Rutas V0.3

- `/`
- `/subvenciones`
- `/subvenciones/[slug]`
- `/subvenciones/region/[slug]`
- `/subvenciones/sector`
- `/subvenciones/sector/[slug]`
- `/subvenciones/organismo`
- `/subvenciones/organismo/[slug]`
- `/subvenciones/beneficiario`
- `/subvenciones/beneficiario/[slug]`

No se implementarán todavía combinaciones programáticas de región + sector.

Copy provisional congelado para V0.3: `Encuentra oportunidades públicas que encajen contigo`; subcopy `Busca y explora subvenciones y ayudas públicas de forma clara, usando información procedente de BDNS.`; CTA principal `Buscar oportunidades`; CTA secundario `Explorar subvenciones`.

## Homepage

- H1 orientado a descubrir y entender oportunidades públicas en España.
- Buscador principal para localizar convocatorias por texto.
- Accesos rápidos a subvenciones, regiones, sectores y beneficiarios.
- Bloque de oportunidades abiertas, identificado con el estado de BDNS.
- Navegación por regiones y sectores con densidad suficiente.
- Señal visible de confianza y procedencia: BDNS/SNPSAP como fuente oficial inicial.
- Estadísticas sólo cuando sean honestas y estén acompañadas de contexto sobre el dataset parcial; no presentar cobertura local como cobertura nacional completa.

## Resultados

Cada card de convocatoria debe poder mostrar, cuando exista:

- título;
- organismo;
- regiones;
- sectores;
- tipo de beneficiario;
- presupuesto;
- estado;
- fechas relevantes;
- código BDNS.

Los campos ausentes deben tener estados explícitos, nunca valores inventados.

## Filtros

- texto;
- región;
- sector;
- beneficiario;
- abierta;
- presupuesto;
- fechas, sólo cuando sean fiables y su semántica esté clara;
- ordenación.

## `is_open`

La UI mostrará literalmente el estado recibido de BDNS y no inferirá el cierre a partir de fechas incompletas.

Cuando `is_open=true` y `end_date=NULL`, mostrar literalmente:

> Abierta según BDNS · sin fecha límite indicada

No se debe inferir una fecha de cierre ni presentar como cerrado un registro sólo porque falte una fecha.

## Ficha

El orden funcional de la ficha será:

1. resumen;
2. presupuesto;
3. organismo;
4. beneficiarios;
5. regiones;
6. sectores;
7. finalidad;
8. fechas;
9. bases;
10. fuente oficial;
11. convocatorias relacionadas futuras.

## Estados de interfaz

La experiencia debe contemplar de forma explícita:

- `loading`, cuando proceda;
- `empty`;
- `error`;
- `no date`;
- `unknown budget`;
- `no funds`.

## SEO

Serán potencialmente indexables, si cumplen el umbral de utilidad y densidad:

- detalle de convocatoria;
- región;
- sector;
- organismo;
- beneficiario.

Llevarán `noindex` los filtros arbitrarios, las búsquedas internas y las combinaciones sin densidad suficiente. No se generarán páginas programáticas indiscriminadas ni thin content.

## Accesibilidad

- Un único H1 por página.
- Labels asociados a controles y filtros.
- Navegación completa mediante teclado.
- Foco visible y ordenado.
- Contraste suficiente.
- HTML y landmarks semánticos.

## Responsive

La especificación debe validarse conceptualmente, como mínimo, en:

- 320 px;
- 390 px;
- 768 px;
- 1024 px;
- 1440 px.

## No incluir todavía

- autenticación;
- alertas;
- IA;
- pagos;
- publicidad;
- afiliación;
- API pública.
